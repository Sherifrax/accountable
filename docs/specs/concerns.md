# Concerns

These need a decision or awareness before building. Each one says what this spec does about it for now.

1. **Six stages, five brand colors.** The brand gives five colors in a set order (Sea Green, Marigold, Coral, Cerulean, Raspberry). The pipeline has six stages, and Raspberry is also the alert color for late deals and overdue follow-ups. Using Raspberry for a stage would make late deals hard to see. **For now:** New is Cerulean, Qualified is Marigold, Proposal is Coral, Negotiation is a light Midnight, Won is Sea Green and Lost is a neutral grey. Raspberry is kept for alerts only. This departs from the brand's order on purpose, so Won reads as success. **Decided:** agreed.
2. **Some brand colors fail contrast for text.** Sea Green and Marigold are too light for text on white, as the brand says. Cerulean with white text (about 3.9:1) and Raspberry with white text (about 3.4:1) are also below the WCAG AA minimum of 4.5:1 for normal-size text. **For now:** a darker text shade is defined for each color (see Design tokens). White text on Cerulean or Raspberry is used only at 14px semibold or larger, such as buttons, and never for small labels. **Decided:** agreed.
3. **"One command" needs a one-time setup.** `npm run dev` only works after Node, uv and `npm install` are in place, which is a lot to ask of someone non-technical (success criterion 1). **For now:** `docs/STATUS.md` lists the prerequisites and the one-time `npm install`. After that, `npm run dev` is the only command, because `uv run` installs the Python packages itself. If one command from a fresh clone is needed, `npm run dev` could run `npm install` first. **Decided:** keep it as is for now. Revisit if a fresh-clone single command is needed. *Since the multi-user change `npm run dev` also needs the three settings in `.env` (R-AUTH-12).*
4. **No internet means no Google Fonts at run time.** The brand fonts come from Google Fonts, but the app must work offline. **For now:** the fonts are installed as npm packages (`@fontsource-variable/instrument-sans`, `@fontsource/instrument-serif`, `@fontsource-variable/jetbrains-mono`) and bundled with the app. They are the same Google Fonts, served locally. **Decided:** agreed, and every font has a secondary (fallback) font from the system, so text still looks right if a bundled font fails to load or while it loads. See the font stacks in Design tokens. *Since the multi-user change the app needs an internet connection for Supabase (R-RUN-5), but the fonts stay bundled, so nothing else is fetched at run time.*
5. **Moving a deal out of Won or Lost.** The intent says the close date becomes today on Won or Lost, but not what happens if the deal is moved back to an open stage. **For now:** the close date stays as it is. The deal may then show as late, which is a fair prompt to set a new date.
6. **What counts as "upcoming".** The intent says follow-ups show as upcoming or overdue, but doesn't say how far ahead "upcoming" looks. **For now:** overdue means the date is before today. Upcoming means today or the next 7 days. Later ones show on their record's timeline, but not on the dashboard.
7. **Stage-change entries.** The intent says they appear by themselves. It doesn't say whether they can be edited. **For now:** they can't be edited or deleted, so the history stays true. They are deleted along with their deal.
8. **The deal's contact changes later.** An activity logged on a deal is also linked to the deal's main contact at that moment. **For now:** changing the deal's contact later doesn't move old activities, because they happened with the person they happened with.
9. **The funnel's meaning.** "How much value reaches each stage" could mean the value sitting in each stage now, or the value that ever got that far. **For now:** it means the value of deals that ever got that far, worked out from stage history (see Dashboard). This is the classic funnel shape, and the open pipeline is shown separately.
10. **The Playwright tests need Google Chrome installed.** This is fine on a developer's machine, but it is a dependency to note in `docs/STATUS.md`.

**Added by the multi-user change** (`docs/changes/multi-user/intent.md`). Where it disagrees with `docs/intent.md`, it wins: it brings in sign-in, several users, dark mode and the need for an internet connection.

11. **`npm run seed` could wipe the team's data.** The intent says "delete all data and load the sample data" (R-RUN-2), and the database is now shared. **For now:** the seed refuses a Postgres database that already has records unless it's given `--force`, and names the host first.
12. **"Today" is the server's date.** The app now has users in more than one time zone, and Render runs on UTC. **For now:** late deals, overdue follow-ups and "Won this month" use the server's date (R-DATA-8), so near midnight someone in the Americas may see a day's difference. Timestamps are stored in UTC and shown in each viewer's time zone (R-DATA-12).
13. **Test sign-in is a back door if it leaks into production.** The tests need to sign in with no real password and no Supabase. **For now:** test mode (R-AUTH-11) is switched on only by the test runners. The backend refuses to start in it on anything but a SQLite file, or on Render. The plan should also test that these guards hold.
14. **How the browser gets the Supabase settings.** Every `/api` route must refuse when signed out, so the browser can't fetch the settings from the backend. **For now:** the frontend reads `SUPABASE_URL` and `SUPABASE_PUBLISHABLE_KEY` from `.env` when it's built or started, so Render needs both at build time and at run time (R-DEP-2).
15. **Checking the token needs the project to use Supabase's signing keys.** With only the three settings, the backend can check tokens against the public keys at `SUPABASE_URL`. A project still on the old shared secret can't be checked that way, and the secret isn't one of the settings. **For now:** the spec assumes the project uses signing keys. The plan should confirm that on the real project before building.
16. **New dependencies.** Sign-in in the browser, checking tokens, talking to Postgres, running migrations and a dropdown menu are each work that a library does better than custom code. The intent allows a new dependency only if the plan makes the case. **For now:** the spec names none. The plan must justify each one (or avoid it) and keep it small.
17. **Same search on SQLite and Postgres.** The two lower-case letters differently: SQLite only handles plain English letters, Postgres handles all. **For now:** the spec asks for the same result on both, accents included (R-SRCH-8), and leaves the method to the plan, such as matching in the application.
18. **There is no dark mode button to move.** The intent says the theme moves from the dark mode button into the menu, but the MVP has no dark mode (`docs/intent.md`). **For now:** the menu adds the theme, with new dark tokens (see `docs/specs/design.md`), and no button is removed.
19. **Only the last change is recorded.** Everyone can edit and delete everything, and a record keeps just who added it and who changed it last, not a history, and deleted records leave nothing. **For now:** that is all the intent asks for.
20. **The free plans sleep.** Render's free service stops after about 15 minutes idle and takes up to a minute to wake (R-DEP-8). Supabase's free projects also pause after a week with no use, and need unpausing in its dashboard. **For now:** both are accepted and the spinner covers the wait.
21. **The unit-test limit can't be checked yet.** R-Q-6 says every unit test, old and new, runs in under a second, but the existing tests haven't been timed for it. **For now:** the plan should time them first and fix any slow ones.
22. **Render's free plan can't reach Supabase's direct database address.** It needs the pooler address (R-DEP-7), and that can restrict how the database driver prepares statements. **For now:** the plan picks the pooler mode and driver settings that work with SQLAlchemy.
